# CH20普通自定义声音重启：修复与证据

## 症状和版本区别

集成开发5.61实机曾报告：CH20在1/200连续重触发声音前段并在松手后结束，在1/250却重复整段长声音。相同版本显示曾对应不同包，必须用SHA区分。

| 集成候选 | 改动与结果 |
|---|---|
| 原5.61，包SHA前缀78a0f2 | 没有本次普通kind0门；用户仍报告故障 |
| 终段kind扩展，包3a93b8 | 把特定终段kind纳入循环bootstrap；用户确认此新包仍有1/250整段重复 |
| c4，包96a395 | 不含终段集合扩展，新增普通CUS原生重启门；用户随后报告当前版本声音正常 |

公开v15是这一c4语义修复在独立mark2固定BSS布局上的适配，仍针对原版5.32，不是集成5.61的同一字节包。完整身份与验证边界见[验证说明](validation.md)。

## 实际修复

原生调度器已经判定普通kind0后，会按两个原生时间值及连续标志判断是否复用原短资源。自定义PCM可以远长于原资源；沿用这一优化时可能省略停止和新请求，产生整段重复。

v15在该门增加只读谓词：CUS已发布，且Cxx启用、待播尾段、活动尾段三个字段均为零，才进入原生stop→wait→新API路径。其他条件重放原指令，继续原分支。旧请求的kind/active/armed/route字段不能代替本次上游kind0准入。

这个门不清忙位、不伪造完成、不释放已发布PCM，不改变波形、速率、固定切点或加入播放队列。Cxx前50/40ms及停止后剩余尾段逻辑继续保留。代码生成器保存调用者寄存器、NZCV和对齐栈；原指令只从哈希匹配的本地原模块读取。

## 为什么旧QEMU通过不足以证明修复

未修复固件的53个旧门样本没有一次进入短复用窗口，帧间隔约65ms。坏基线与修复候选都可以在该模拟条件下通过，成片和PCM数量不能证明坏分支被覆盖。c4新冷34JPEG/34PCM仅证明相应配方的拍摄、重按、松手尾音回归；实机症状接受来自用户后续反馈。

追加官方原版、无镜头、原生A声音对照也出现约62.67～65.64ms间隔，33JPEG/33PCM均通过。因此长自定义WAV不是模拟慢节拍的唯一原因，当前仓库不宣称修复QEMU或获得额定20fps。

历史c4的32次直接stop32调用与原生计算的截止时间接近；原版A则从另一个定时器栈调用stop32。原版31分配/提交/处理在新增窄点样本中为微秒量级，不能把前后约19ms都算成消息排队。下一步模型研究仍需直接观察有界等待的参数、返回原因以及生产时间戳来源。

## 跨机型需要重新验证的合同

Z9接口地址仅属于5.32映射。消息请求04210031/32，处理后回调04212001/02，声音通知04212004/05分别编号。时间上相邻不证明同一同步调用，须同时记录LR、栈及CPU；CPU/栈也不自动成为任务身份。Z9计时函数的计数/24与对应24MHz模型相符，这不能替代Z8计时器证据。

移植时应先获取目标机的kind路径与复用门，再恢复原生停止/等待/回调合同。动态内存布局必须增加正确的ready检查；固定BSS不能照搬heap锚点。合成组件、AArch64寄存器、完整重建、模拟拍摄、设备接受和长期验证分开登记。
